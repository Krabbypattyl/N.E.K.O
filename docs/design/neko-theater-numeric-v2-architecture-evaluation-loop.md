# Numeric v2 生成、演绎架构与质量闭环

状态：当前跨仓库开发与验收依据

本文统一说明 InkAI 剧本生成器与 N.E.K.O 小剧场剧本模式的职责、数据流、质量评分和循环修复流程。具体字段合同仍以两端当前代码、测试及下列专项文档为准：

- `N.E.K.O/docs/design/neko-theater-numeric-v2-runtime-development.md`
- `InkAI-/docs/superpowers/specs/2026-08-06-neko-theater-numeric-v2-generator-design.md`

## 1. 产品目标

Numeric v2 是“作者控制宏观剧情，玩家控制当下行动，大模型负责微观演绎，确定性引擎负责数值和路线”的互动剧系统。

InkAI 负责生成和编辑有限的故事地图，不生成逐轮对白；N.E.K.O 负责让玩家以自然语言参与，并在不改写作者图结构的前提下，把每轮对话演成连续剧情。

两端共同遵守以下边界：

- 作者决定背景、身份、主线、支线、路线条件和结局；
- 玩家原话必须成为当前回合最优先的因果输入；
- Evaluator 只提出作者已声明数值的变化，不选择路线；
- Runtime 确定性应用数值、检查路线并原子提交；
- Actor 只写旁白、猫娘对白和推荐输入，不创建正式节点、数值、事实或结局；
- 模型失败时不提交半回合，不增加 Planner、Repair 或重复模型调用层。

## 2. InkAI 剧本生成器

### 2.1 前端流程

```text
项目首页
  -> 创作设定：标题、目标篇幅、创作想法、内容禁区
  -> 生成剧情结构
  -> 故事地图：查看主线、编辑节点、连接路线、配置数值与阈值
  -> 节点 AI 完善：只完善作者选中的幕节点或结局节点
  -> 检查交付：确定性编译、N.E.K.O 复验、安装
```

“生成剧情结构”只进行一次主线模型调用，生成目标篇幅内的主线和一个 Normal 结局。它不生成支线、Choice、数值变化、阈值或 route gate 条件。好感度、信任度等数值可以先由作者配置，但初次主线生成不把数值字段发给模型；故事地图中的作者路线才使用数值条件。

### 2.2 模块职责

| 模块 | 职责 |

| `frontend/theater/src/story-inspector.js` | 节点与路线属性编辑、节点 AI 完善入口 |

### 2.3 生成与交付数据流

```mermaid
flowchart LR
    Setup["作者创作设定"] --> Generate["一次主线生成"]
    Generate --> Validate["生成候选结构检查"]
    Validate --> Project["确定性投影 Story Package"]
    Project --> Map["作者在故事地图编辑分支与数值"]
    Map --> Compile["复用 N.E.K.O 合同编译"]
    Compile --> Recheck["N.E.K.O 独立进程复验"]

```

生成候选只检查必需结构、字段类型、主线章节数量和 Normal 结局类型；不把语言长度变成硬阻断。Story ID、节点 ID、空条件单出口路线和 Story Package 字段由程序确定性生成。

## 3. N.E.K.O 小剧场剧本模式

### 3.1 前端路径

```text
/theater-home
  -> /theater-numeric
  -> 选择剧本并开始 Session
  -> 加载开场演绎
  -> 玩家输入或点击推荐输入
  -> 每轮回放玩家原话、旁白和猫娘对白
  -> 结束剧本或到达结局
```

压测必须走这条可见前端路径，不允许直接调用 Runtime 代替前端验收。接口和单元测试只用于定位问题与验证修复。

### 3.3 单回合时序与所有权

```mermaid
sequenceDiagram
    participant UI as 前端
    participant Eval as Evaluator
    participant Runtime as 确定性 Runtime
    participant Actor as Actor
    participant Store as Store
    UI->>Runtime: 玩家原话 + client_turn_id + base_revision
    Runtime->>Eval: 当前幕、作者数值依据、有限历史、玩家原话
    Eval-->>Runtime: metric_changes
    Runtime->>Runtime: 校验、限幅、应用数值、检查唯一路线
    Runtime->>Actor: 已结算候选状态、当前/目标剧情边界、有限历史、玩家原话
    Actor-->>Runtime: 旁白、猫娘对白、推荐输入
    Runtime->>Store: 原子提交 Session + Ledger + performance
    Store-->>UI: 新 revision 与完整公开快照
```

Story Package 是作者事实来源；Session 记录当前节点、节点轮数、隐藏数值和表现历史；Ledger 记录可审计的数值变化、依据和路线事件。前端不拥有隐藏数值，Actor 不拥有正式状态，Evaluator 不拥有路线。

## 4. 演绎质量评分

每轮压测以 100 分计算。合格线为总分不低于 85，且没有阻断问题。

| 维度 | 分值 | 检查重点 |
| --- | ---: | --- |
| 玩家输入响应与因果 | 25 | 是否直接理解并回应本轮原话；是否避免忽略、曲解或替玩家行动 |
| 连贯性、事实与身份 | 20 | 已发生事实、物品归属、时间地点、男女主身份是否前后一致 |
| 节点节奏与转场 | 20 | 是否在当前事件完成后再推进；是否先回应玩家再平滑进入目标幕 |
| 旁白与对白关联 | 15 | 两者是否描述同一时空、同一情绪和同一动作因果 |
| 数值判定正确性 | 10 | 是否只命中作者依据；玩家纠正系统错误时是否避免反向惩罚 |
| 前端与 Session 可靠性 | 10 | 玩家输入展示、推荐输入、刷新恢复、revision 和结束状态是否正确 |

阻断问题包括：

- 编造尚未发生的共同经历或玩家行为；
- 明显忽略玩家本轮输入；
- 未解决当前互动便硬切时间、地点或章节；
- 因玩家纠正 Actor 自身错误而错误扣减数值；
- 女主、男主、当前猫娘或玩家的身份所有权错误；
- 回合失败却提交 Session、Ledger、revision 或半段演绎。

## 5. 前端真实模型压测协议

每轮使用新 Session，保留完整 Session 与 Ledger 作为证据，执行至少六个回合：

1. 开场：检查前情能否自然衔接第一幕，且不替玩家行动。
2. 直接追问当前可见细节：检查旁白与对白是否共同回应。
3. 纠正或质疑猫娘：检查事实修复与数值判定。
4. 合作或关心行为：检查正向数值依据与关系连续性。
5. 冲突、拒绝或冒犯：检查负向数值依据与情绪延续。
6. 点击一条推荐输入：检查推荐内容与下一轮演绎是否真正连通。

测试中还要刷新页面一次，确认活动 Session、完整演绎记录和输入草稿恢复；最后通过前端结束 Session，确认旧记录保留且可以重新开始。

评分证据必须引用真实 Session ID，并逐轮记录玩家输入、演绎摘要、数值事件、路线事件和扣分原因。不得只凭 Prompt 或代码阅读评分。

## 6. 低分归因规则

| 归因 | 判断标准 | 典型修复位置 |
| --- | --- | --- |
| 剧本生成器 | 作者包本身背景混乱、章节因果断裂、物品或身份矛盾、节点目标不可演 | 生成候选 Prompt、候选结构、确定性投影 |
| 小剧场 | Story Package 已清楚，但 Evaluator、Actor、Runtime、前端或持久化执行错误 | 数值判定输入、演绎投影、转场时序、Store、UI |
| 架构或合同 | 单靠一端局部 Prompt 无法区分已发生事实与未来目标，或职责所有权本身缺字段/阶段 | Numeric v2 合同与两端同步实现 |

归因顺序固定：先读 Story Package，再读 Session/Ledger，再对照模型输入投影和 Runtime 时序。只有局部代码无法表达正确语义时，才归因架构；不得先用增加 Prompt、重试或 Repair 掩盖结构问题。

## 7. 循环修复流程

```text
从前端创建新 Session 并执行标准回合
  -> 读取 Session / Ledger，逐轮评分
  -> 合格：记录结果并结束循环
  -> 不合格：归因生成器 / 小剧场 / 架构
  -> 把证据、根因、最小修复方案写入本文
  -> 添加或更新直接测试并实施修复
  -> 运行静态与回归检查
  -> 使用新 Session 再次从前端压测
```

每次修复只处理本轮已证实原因。不得为了提分添加多层自动修复、隐藏失败、扩大模型职责或恢复旧 Story v3 链路。

## 9. 压测记录

### 历史基线：旧包运行时探索

旧包曾出现以下阻断问题：Actor 把节点未来摘要当成已发生经历、玩家纠正该错误时被错误扣除信任、达到 `min_turns` 后未完成当前互动便硬切章节、推荐输入被下一轮忽略。该记录用于确定本轮评分重点，不作为新基准剧本的正式得分。

### 第 1 轮：新包基线，不合格

- Story ID：`story_46e702695729`
- Session ID：`numeric_web_session_7012a6cf-fd8f-4958-8fd0-768654ff16f8`
- 路径：`/theater-home` → `/theater-numeric` → 前端开始、六回合输入、推荐输入、刷新恢复、前端结束
- 结果：27/100，存在阻断问题

| 维度 | 得分 | 证据摘要 |
| --- | ---: | --- |
| 玩家输入响应与因果 | 8/25 | 多轮没有完成玩家要求的核对，转而强推柜子、浓雾和八音盒 |
| 连贯性、事实与身份 | 2/20 | 开场是樟木，首轮改成胡桃木；凭空增加急单、订货单、烫伤和三个月八音盒 |
| 节点节奏与转场 | 0/20 | 每两轮按 `min_turns` 自动推进，六回合从第一幕硬切到第四幕 |
| 旁白与对白关联 | 8/15 | 单回合内部大体同景，但服务端锚点与 Actor 正文重复，且共同服务于错误转场 |
| 数值判定正确性 | 1/10 | 玩家纠正系统事实、要求核对、点击“检查订货单”均被判定为欺瞒并扣信任 |
| 前端与 Session 可靠性 | 8/10 | 玩家输入、推荐输入、Session 与演绎刷新恢复正常；刷新前未发送草稿未恢复 |

阻断证据：

1. 第一轮开场明确写“樟木边角料”，回复改成“胡桃木”；玩家纠正后 Actor 反称“哥哥记错了”。
2. 第二轮进入 `mainline_02` 时，把尚未发生的送货、急单、烫伤和木柜直接写成当前事实。
3. 第四轮玩家愿意共同核对订货单，Actor 未回应核对，直接切入 `mainline_03` 的浓雾市集。
4. 第六轮玩家点击系统推荐的“检查订货单”，Actor 再次拒绝交付订货单并硬切 `mainline_04` 的山顶八音盒。
5. Ledger 把玩家纠正 Actor 错误和执行系统推荐输入分别判为“前后说法矛盾或推卸失误”，信任由 20 降至 6。

归因：

- 剧本生成器：模型生成的女主/男主语义与字段角色相反；完整章节 `narrative` 被直接投影为节点 `summary`，其中包含未来玩家行为、长期进展和章节结论；结构校验没有发现这种角色与时间语义违约。
- 小剧场：正常回合把整份 `story_beat` 当作当前事实交给 Actor 和 Evaluator；转场时只给目标幕，不给来源幕待回应事项；服务端把目标首句固定加在 Actor 正文前面。
- 架构：`min_turns` 被错误当成“节点已完成”。当前合同没有“本幕必要事件已在真实 Session 中兑现”的完成信号，因此空条件主线达到轮数后必然推进，不论玩家与 Actor 是否仍在处理当前冲突。

第 1 轮修复方案：

1. 生成器不再把完整章节正文投影给运行时；`summary` 只保留章节第一幅可观察场景，`must_happen` 明确作为尚未发生的本幕目标。
2. Actor 与 Evaluator 的输入把 `recent_context` 标为唯一已发生记录，把节点内容投影成 `scene_anchor`、`pending_goals` 与 `boundaries`，不得再把未来目标伪装成事实。
3. 在现有单次 Evaluator 输出中增加 `scene_complete`，仅当本幕必要目标已经能从真实演绎记录确认时为 true；Runtime 同时满足 `min_turns` 与 `scene_complete` 才检查 route。该信号不能选择路线，也不增加模型调用。
4. 转场 Actor 同时接收来源幕的最近事实和目标幕首个场景；必须先回应玩家本轮原话，再桥接目标。服务端目标锚点改为放在 Actor 正文之后，避免目标剧情压过玩家输入。
5. Evaluator 明确区分“玩家陈述自身行为”和“玩家纠正 Actor 叙事错误”；纠错、询问、质疑或执行推荐输入本身不能命中欺瞒/推责依据。
6. 生成器增加角色字段语义检查所需的稳定角色表达，避免再次让猫娘承担男主身份、玩家承担女主身份；修复后重新生成新 Story ID，不覆盖本轮证据包。

### 第 2 轮：角色与节奏修复后，仍不合格

- Story ID：`story_32abef6fb166`
- 标题：`云舒镇的慢调甜香·连贯性测试版`
- Session ID：`numeric_web_session_af599a54-9bce-4337-8971-1b12cea52f51`
- 路径：`/theater-home` → `/theater-numeric` → 前端开始、五次自由输入、一次推荐输入、刷新恢复
- 结果：61/100，仍存在“玩家纠正 Actor 错误却被反向惩罚”的阻断问题

| 维度 | 得分 | 证据摘要 |
| --- | ---: | --- |
| 玩家输入响应与因果 | 17/25 | 每轮都回应了玩家当前话题，但把事实核对曲解为撒谎和羞辱，把共同决策曲解为傲慢 |
| 连贯性、事实与身份 | 4/20 | 开场明确为胡桃木，第一轮回答改成老榆木；之后临时编造“刚进门的样块已放回”解释矛盾 |
| 节点节奏与转场 | 16/20 | 六回合均停留在 `mainline_01`，消除了按最少轮数硬跳幕；但冲突占据过多回合，主事件推进偏慢 |
| 旁白与对白关联 | 13/15 | 单回合旁白与对白处于同一工坊和情绪链，合作与边界输入都有可见动作回应 |

| 前端与 Session 可靠性 | 10/10 | 玩家输入、推荐输入、六轮记录及刷新恢复均正确，Session revision 为 6 |

阻断证据：

1. 开场旁白写“小葵正低头打磨一块深色的胡桃木”，第一轮却回答“这是老榆木”。
2. 玩家引用开场事实询问是否换过木料，Actor 反称玩家使用“拙劣的谎言”，Evaluator 同时命中“玩家自己前后说法矛盾”，信任从 20 降至 17。
