本文是 N.E.K.O 仓库内小剧场的历史实测问题文档。这里只记录有代码链、日志、Session/Ledger 或真实前端回放证据的问题；产品与技术合同见[小剧场架构开发文档](./neko-theater-architecture.md)。文中旧包、旧 Session 和旧 Prompt 的兼容结论只代表当时证据，不代表当前运行语义；当前旧包必须先升级到 v2.2。

## 1. 记录规则

每个问题必须包含：

1. 可复现输入或操作路径；
2. Story ID、Session ID、revision 或其他证据锚点；
3. 玩家实际看见的结果与正式状态；

### 问题 1：正式节点已推进，但可见场景没有切换

状态：**已修复待真实前端复测**
发现日期：2026-08-14

#### 2.1 玩家现象

玩家在暴雨夜被允许暂住后，正式剧情本应进入“合租第二天的秋刀鱼晚餐”。页面没有出现时间和场景过渡，Actor 仍围绕暴雨夜、客厅、毛毯、剪刀和烧水继续演绎。

玩家随后明确输入：

- `行行行，我整点热水喝了就休息了`
- `睡了`
- `保持沉默，直接休息`

Actor 虽然描写了短暂安静，却继续输出：

- `……最好是真的睡了。要是敢半夜偷东西，我就剪断你的手指。`
- `……装睡也没用。我听得见你的呼吸声。`

并继续推荐“保持沉默，继续装睡”“询问她是否也去休息”等旧场景交互。玩家已经明确结束当晚交流，演绎仍把他拉回同一段对话，没有平滑过渡到第二天。

#### 2.2 可复现证据

- Story ID：`story_3e874621e937`
- Session ID：`numeric_web_session_a7a29c4d-a1bf-4713-87b8-8e8d3c24ed77`
- Session 文件：`~/Library/Application Support/N.E.K.O/theater/numeric_v2/sessions/numeric_web_session_a7a29c4d-a1bf-4713-87b8-8e8d3c24ed77.json`
- 文件更新时间：2026-08-14 10:04:05 +0800
- 最终快照：`status=active`、`revision=12`、`current_node_id=mainline_02`、`node_turn_count=7`

关键 Ledger：

| revision | 玩家输入 | 正式节点 | `scene_complete` | `route_status` |
| ---: | --- | --- | --- | --- |
| 4 | `所以今晚我是能呆在这了吧` | `mainline_01 → mainline_01` | false | `scene_incomplete` |
| 5 | `这大雨天的哪有光` | `mainline_01 → mainline_02` | true | `advanced` |

`mainline_02` 的正式作者目标是：

- 章节：`第二章：秋刀鱼的香气`
- 时间：合租第二天傍晚
- 场景：男主炙烤秋刀鱼并准备味噌汤
- 必须发生：女主走出房间，与男主共进晚餐，首次接受男主提供的食物

`route_mainline_01_02.transition_contract.must_deliver` 也要求明确换场到合租第二天、秋刀鱼和晚餐。revision 5 的 Actor 结果却仍是夜色渐深、暴雨、沙发和剪刀，没有建立目标节点开场。revision 6—12 虽然正式节点已经是 `mainline_02`，可见事实仍沿用旧雨夜，因此 Evaluator 一直无法从当前演绎确认“第二天共进秋刀鱼晚餐”的 `pending_goals`。

#### 2.3 已确认根因

这不是 Runtime 不会自动推进节点。revision 5 已证明 Runtime 正确选择 `route_mainline_01_02`，并把 Session 的正式节点改为 `mainline_02`。

问题发生在“正式推进”与“可见演绎”之间：

1. Router 向 Actor 传入了 `route_changed=true`、来源节点、目标节点、目标 `opening_scene` 和 `transition_contract`；
2. Actor Prompt 要求回应当前输入、收住来源互动并桥接目标开场；
3. Actor 输出解析器只校验 JSON、字段、对白 speaker 和文本形状，没有验证换场段是否存在或是否交付目标开场；
4. 该输出随后与已经推进到目标节点的 Session 一起原子提交；
5. Numeric 前端按当前产品约定不显示节点标题或场景卡，只显示 Actor 表现，因此玩家看不到 Runtime 已经换节点；
6. 下一轮 Evaluator 以 `mainline_02` 的目标判定，却只能看到 Actor 留下的旧场景事实，形成“正式节点向前、可见剧情卡在原地”的闭锁。

所以，这是 **Actor 换场交付没有成为提交不变量**，不是路由条件、`min_turns`、前端按钮或 Session 恢复问题。

#### 2.4 为什么不能用“识别睡觉后直接进下一幕”修复

玩家输入“睡了”时，Runtime 已经处于 `mainline_02`。如果把休息关键词直接解释成节点推进，会从尚未演出的秋刀鱼晚餐跳到 `mainline_03`，再次绕过作者 `must_happen`，并让 Runtime 承担自然语言意图分类。这会破坏既定模型权限和确定性路线合同。

休息类输入应按当前正式状态处理：

- 当前幕未完成：允许 Actor 收住即时交流、描写时间流逝或休息，但不能跳过本幕目标；
- 当前幕完成且 Runtime 已选择路线：休息、离开、结束交谈可以成为过渡到下一场景或第二天的自然桥；
- 不根据单个关键词新增隐式路线，也不让 Actor 自己决定目标节点。

#### 2.5 解决方案

方案目标是让“正式节点”和“玩家看见的场景”在同一个原子提交内保持一致，不增加 Planner、Repair、自动评分模型或第二次 Actor 调用。

1. **把换场输出结构化。** `route_changed=true` 时，同一次 Actor 输出必须分别提供来源回应、过渡桥和目标开场三个非空段；普通未换场回合继续使用现有简化结构。前端仍可按一段连续演绎展示，不增加章节卡。
2. **让解析失败阻止提交。** 缺少来源回应、过渡桥或目标开场时视为 Actor 合同失败，Session、Ledger 和表现历史都不提交；不能再提交“节点已换但换场正文缺失”的回合。
3. **记录可见节点锚点。** 换场成功的 performance record 保存有序 `segments`、`visible_node_id` 和 `transition_delivered`；Store 复验路线 Ledger 与表现记录一致。恢复时据此确认最后一条可见演绎已经锚定当前节点。
4. **目标开场输入保持确定性。** Actor 只消费 Runtime 已选定的目标 `opening_scene`、`must_deliver` 和 `must_preserve`，不能自行换目标；`target_opening.scene_narration` 必须以目标 `opening_scene` 原文开头，后续正文再自然延展。
5. **收紧休息后的推荐输入。** 玩家明确休息后，如果没有目标场景中的叫醒或紧急事件，不推荐“装睡、继续解释、继续聊天”等反向动作；若本幕仍有待完成目标，用自然时间过渡把演绎带到目标事件发生条件，而不是重复旧对话。
6. **增加软节奏预算。** 非结局节点可声明玩家不可见的 `recommended_turns`。接近预算时 Actor 聚焦本幕目标，达到或超过预算时主动收束重复交流；预算不设置 `scene_complete`、不触发路线，也不限制玩家继续自由输入。

实现保持单次 Actor 调用，没有增加 Planner、Repair、关键词路由或硬性自由发言次数限制，也没有用前端显示节点标题掩盖演绎缺口。

#### 2.6 实现与自动验证

- Actor 在 `route_changed=true` 时只接受 `source_response → transition_bridge → target_opening` 三段结构，缺段、乱序或目标开场不匹配都会失败；
- Runtime 在提交前校验 `transition_delivered`、`visible_node_id` 和 Ledger 目标节点，Store 对带新 performance 合同版本的记录在加载与恢复时再次复验；无版本标记的修复前记录保持兼容；
- 前端按段落顺序渲染换场表现，普通旧 performance 仍走兼容投影；
- `recommended_turns` 已进入 Numeric v2 合同、Actor 节奏提示和生成器节点编辑器；当前生成器默认 `min_turns=3 / recommended_turns=3`、最大 40、不得小于 `min_turns`；
- N.E.K.O 合同、模型、Runtime、Router 和浏览器定向回归共 63 项通过；生成器合同、主线、支线和前端定向回归共 54 项通过；
- 作者项目 `project_301ef5cdee01` 已无模型重生成地更新为 revision 87；修复版 `story_24738dcf0099` 已通过 canonical 编译与 N.E.K.O 复验并安装，package hash 均为 `sha256:7d486957b30cb8055733b3959b3fa1cbcb67f91a6195ad4e5fc0e4518f9ded05`；
- 原包 `story_3e874621e937` 和其 active Session `numeric_web_session_a7a29c4d-a1bf-4713-87b8-8e8d3c24ed77` 保留，未做破坏性覆盖。
- 已用该真实旧 Session 验证兼容恢复：`mainline_02`、revision 12、`status=active` 均保持不变。

#### 2.7 真实复测标准

自动回归至少覆盖：

1. 构造 `mainline_01 → mainline_02` 的 route change，Actor 缺少任一换场段时整回合不提交；
2. 合法换场后 Ledger 的 `to_node_id`、Session `current_node_id` 与 performance 的可见目标锚点一致；
3. 刷新恢复后仍从目标场景继续，不能回到来源场景；
4. 使用本次输入序列回放，revision 5 的可见正文必须出现第二天、厨房/晚餐与秋刀鱼等目标开场事实；
5. 输入“睡了”或“直接休息”后，演绎自然收束，不继续推荐“装睡并交流”；
6. 不允许在晚餐目标未完成时直接推进 `mainline_03`；
7. Evaluator 仍只输出作者 criterion、有限强度、目标证据与 `scene_complete`，服务端确定性换算 delta，Runtime 仍只按作者路线推进，模型调用次数不增加；
8. 真实前端模型复测通过后，才能把状态改为“实测通过”。

### 问题 2：连续回合只有旁白，没有猫娘对白

状态：**已修复待真实前端复测**
发现日期：2026-08-14

#### 2.8 证据与根因

- Story ID：`story_24738dcf0099`
- Session ID：`numeric_web_session_265f1017-6163-4c6b-bc01-d2dd32a0df3f`
- revision 2—4 的 performance 均有旁白，但 `dialogue=[]`；前端和 TTS 因而没有可显示、可播放的对白。
- revision 2 仍处于软节奏 `normal`，所以问题不是软预算单独造成；revision 3、4 的 `focus/closure` 可能进一步强化动作和环境描写倾向。
- 旧 Actor DTO 把 `narration` 与 `dialogue[]` 分离，天然只能先显示全部旁白、再显示全部对白；解析器又允许“有旁白、无对白”提交，并会静默过滤非法对白项。
- 原始模型输出没有持久化，历史记录无法区分模型主动返回空数组，还是对白项被过滤，这是附带的可观测性缺口。

#### 2.9 解决方案与复测标准

- 新 Actor 输出改为单一 `performance` 混合正文：括号内是微动作，括号外是猫娘对白；动作和对白按实际发生顺序穿插，不限制固定对白句数；
- 普通回合必须同时包含至少一个括号动作和有效猫娘对白；括号不成对、嵌套括号、空文本或纯动作输出整回合失败，不再提交静默降级结果；
- 换场仍保留三段结构，但每段内部使用相同内容块；来源回应至少有一句对白；
- Actor 与 Evaluator 的历史上下文、前端恢复、TTS 提取都消费同一顺序；TTS 只朗读对白，并保持多句对白的先后次序；
- 旧 `narration/dialogue` 和旧换场段继续兼容显示与恢复，不重写已提交历史；
- 使用修复版剧本继续演绎，至少验证一个普通回合包含“动作 → 多句对白 → 动作 → 对白”，刷新后原始顺序不变，才能标记为“实测通过”。

- 自动回归必须验证开场可见当前标题、换场可见来源与目标标题，且软锚点的优先级限制仍完整保留；
- 真实前端模型复测需使用同一幕同时包含主题道具与次要道具、玩家使用模糊指代的用例，确认 Actor 优先围绕章节标题所指主题展开。

### 问题 5：起手句式模板化，不同角色卡的演绎趋同

#### 2.15 证据与根因

- 最近四个可读取 Session 的 revision 2 首段分别使用“听到‘权利’二字”“听到‘中介’二字”“听到这句近乎无赖的宣言”和“听到那声无奈的叹息”等同构起手；最新 Session 的 revision 3 又出现“听到‘洗澡’二字”，因此不是第二回合固定分支；

- 该问题不是单个禁词问题。若硬禁“听到”或“闻言”，模型只会替换为“面对这番话”等同义模板，同时进一步削弱角色自然表达。

#### 2.16 优化方案与复测标准

- 从通用 System Prompt 移出角色人格，把角色卡人格放入开场和每回合 Human Prompt 尾部的 `acting_context.core_persona`，使其靠近当前输入并保持 160 Token 上限；

- 增加软文风合同：角色卡决定措辞、句长、主动性和情绪外显方式；“听到”“闻言”不是禁词，旁白减少替作者评价玩家，且不能为求变化破坏人格和事实；
- 不增加基于回合号的模板轮换，也不因为单个句式相似而拒绝提交；现有近重复保护继续只处理整轮内容照搬；
- 自动回归必须验证不同角色人格会形成不同的 `acting_context.core_persona`、该字段靠近当前输入、最近起手句按完整句投影、总 Prompt 不超过 4800 Token，且最新事实记忆不被二次裁剪；

### 问题 7：开场推荐输入被格式示例污染并跨剧本串线

#### 2.20 证据、根因与修复方向

真实压测中，《猫尾特调恋爱指南》的第一次开场推荐输入为：

#### 2.23 证据、边界与修复方向

《月台尽头的猫灯》第一次真实压测在第 12 回合准备从 `mainline_02` 换场时，Actor 返回结果没有满足目标开场前缀合同，抛出：

第 11 轮首次压测生成 3 个开场、16 个完整回合和 3 次换场，共 59 条推荐输入；没有出现“我把……”“我拿……”式机械动作。修复后再次定向运行《猫尾特调恋爱指南》，开场及 4 个回合的推荐台词全部使用中文引号，动作项均从动作动词起笔，操作说明与意图摘要命中数为 0。

### 问题 16：换场桥与确定性目标开场重复，单次可见换场过长

### 问题 17：换场来源回应复读上一轮，目标场景掩盖整轮近重复

第 11 轮《猫尾特调恋爱指南》第 5 回合已经说“既然签了字，那现在就是正式员工啦”“先去厨房熟悉一下环境”，第 6 回合换场的 `source_response` 又逐字重复两句。既有近重复保护比较整个换场正文，后续桥段和目标开场拉低了整体相似度，因此无法识别来源段复读。

### 问题 18：隐藏关系仍在最低阶段，可见演绎已经提前进入粘人状态

状态：**Actor 合同、数值结算和未来生成默认已修复，真实模型定向复测通过；完整前端关系弧待验收**

#### 2.32 证据与修复方向

最新正式《云舒镇的奇遇》Session 在第 10 回合仍处于好感 `礼貌疏离` band，但猫娘已连续使用“麻烦哥哥了”“人家会乖乖等着的”“等着吃鱼了哦”等明显依赖式表达。当前节点实际已经停留 4 回合，上一节点停留 6 回合，因此根因不是 Runtime 提前越过 `min_turns`，而是 Actor 只拿到 band 文案，没有被明确要求把它作为可见亲密度上限；角色卡中的甜美、温柔、粘人又被模型误解成当前关系已经建立。开场警惕一度被演成威胁，也放大了随后软化的突变感。

关系型 metric 现只由 Story Package 显式 `relationship_effect` 识别，正向和反向数值统一投影为 `stranger / guarded / cooperative / trusted / intimate`，多个关系数值再与当前幕关系上限取最严格者。最低阶段只允许基本礼貌、有限软化和保持距离，不得主动暧昧、占有、依赖或使用伴侣式亲昵称呼；较高阶段仍须由已发生事实支撑。核心人格继续决定表达方式，不能用于越过关系阶段，低关系也不授权敌视、羞辱或威胁。

当前回合 Actor 使用结算前关系数值，跨 band 后从下一回合才改变可见关系，避免一次行动触发瞬时亲密跳变；非关系能力状态仍可使用结算后的候选数值。Evaluator 不再直接返回任意 delta，只选择作者 criterion 和 `weak / normal / strong / decisive`，服务端按单回合限幅确定性换算；最近四条 Ledger 已奖励过同一关系依据时，重复礼貌、换一种说法或延续同一态度不能继续刷值，除非出现新成本、风险、兑现或可验证结果。

关系语义不再使用“乖乖听话”“都听你的”、抓拉、贴近等有限关键词正则做提交前硬校验。此类校验无法覆盖同义改写，并会把自然配合误判成关系越级；同一次 Actor 自报检查也在真实探针中出现过正文写“顺从地垂落”、检查却声明无依赖的矛盾，不能作为提交依据。Runtime 现按 `effective_stage` 投影阶段化 `response_contract`，在核心人格之后最后收口本轮正文与推荐输入的允许姿态；生成器同时把未来主线和支线默认节奏调整为 `min_turns: 3 / recommended_turns: 3`，新建数值默认范围为 `0—50`，关系型数值默认单回合增减上限为 3，非关系型保持 5，并要求亲密关系主线按关系弧逐幕推进。

真实模型定向复测使用新 Story ID、新 Session 和当前小葵角色卡连续演绎 10 回合：第一幕在第 8 回合才换场，关系数值最终为 2，仍处于 `guarded`；“观察、检查安全”等泛化行为没有误加黑客能力。换场在 4800 Token Actor 输入预算内完成。初次压力探针仍捕获了抓衣袖、主动靠近和摸头推荐语；改为阶段化响应合同并调整上下文优先级后，相同低关系输入连续 5 次真实 Actor 抽测均保持静止、自检、观察或追问，没有再出现讨好式服从。三处支线阈值状态的真实 Actor 换场探针均成功生成合法三段式过渡，并分别保持各自计算出的关系上限。以上证明当前单次生成合同明显改善低关系表现，但在不增加语义分类模型或 Repair 的边界下不宣称百分之百硬拦截，仍需真实前端从低关系连续演到高关系的完整体验验收。

### 问题 19：称呼在 Session 初始未知前被 Actor 提前使用

状态：**代码已修复待真实前端复测**

#### 2.33 证据与根因

旧链路把配置中的玩家昵称无条件写入猫娘绑定，并在 opening、普通回合和换场 Prompt 中直接告诉 Actor。即使剧本语义上要求开场不知道称呼，真实模型仍可能在第一回合提前叫出昵称；自然语言关键词拦截无法覆盖同义表达，也不能安全推断“称呼未知”。

#### 2.34 解决方案与回归标准

- Story Package 的 `initial_state` 增加结构化 `player_address_known` 布尔值；旧包缺少该字段时只按 `false` 兼容；不从剧情文案解析称呼状态；
- Session 持久化同名状态，重新开始按 Story Package 初始值重置，继续恢复已提交值；旧 Session 缺少字段时仅检查已提交玩家输入中是否出现完整配置昵称；
- 未知阶段 Actor 的所有稳定身份投影统一使用“你”，不接收真实配置昵称；用户本轮精确包含完整昵称时，只把它作为披露候选；
- Runtime 在 Actor 成功后把候选状态与 Ledger、Session、表现历史一起原子提交；Actor 或 Store 失败不能提前修改；
- 未知阶段对 Actor 正文和推荐输入做完整昵称精确字符串保护，不使用语义正则猜测；
- 节点可声明结构化 `story_beat.acting_contract`，明确开机认知、记忆、自称和人格权限；`system_neutral` 阶段隐藏角色卡显式自称事实，违规输出阻止提交，不改写模型正文；
- 自动回归必须覆盖开场、普通回合、换场、失败不落盘、继续恢复和重新开始重置；真实前端复测需用新 Session 验证四类流程，并确认未披露前的 Prompt 与输出不出现配置昵称。

### 问题 20：换场上下文重复且过渡桥会替玩家补写行动

状态：**代码已修复，真实模型定向复测通过；完整前端长程演绎待验收**

#### 2.35 证据与根因

为同时保住来源回应和目标开场，旧换场 Prompt 叠加了完整来源 beat、完整目标 beat、目标自由文本临时状态、两套数值解释、风格说明和历史记录。当前《霓虹下的猫耳重构》实际换场输入因此一度超过 4800 Token；角色卡整段进入 `style_only` 合同时还会夹带关系定位、特殊自称和昵称等非风格事实。压缩后的首轮真实模型探针虽然均返回合法三段结构，但 2/3 的 `transition_bridge` 仍把“切断线路、带她离开”等行动直接分配给用户，说明只靠提示词声明玩家归属仍不足以成为提交不变量。

#### 2.36 解决方案与回归结果

后续产品边界已从“玩家动作绝对禁写”修订为“玩家自主决定保护 + 身体结果因果约束”。原问题仍成立，因为当时桥段无前因地把切断线路和带人离开分配给用户；但有正式事实直接造成的受伤、失衡、条件反射或被外力带动不再视为越权。此类结果必须在同一句交代前因，且不能扩写成玩家对白、承诺、路线或关系选择。

- 换场在通用预算装箱前使用确定性紧凑投影：保留稳定剧情前提、结构化称呼状态、来源硬边界、目标待完成目标与硬边界、Runtime 目标开场、过渡合同、最近完整历史、两幕演绎/关系合同和本轮输入；删除已消费来源目标、目标自由文本临时状态以及重复的能力、优先级和风格说明；
- `persona_scope=style_only` 只允许结构化标注为性格、行为、喜好、厌恶、口癖、说话风格或语气的角色卡字段进入 Actor，不再携带昵称、特殊自称、关系定位或未标注关系记忆；
- 复合“男女主”身份槽先整体投影为“你和当前猫娘”，再处理单一角色名，避免出现“男小葵”等部分替换；
- `transition_bridge` 允许环境、时间、地点变化及其直接造成的玩家即时身体结果；提交前对玩家主体做因果与自主决定保护：无前因动作或自主决定命中即整回合失败，有同句前因的 A 类身体结果可以原子提交；
- 当前正式剧本换场 Prompt 从约 5743 Token 降至 4018 Token。增加保护后的真实模型连续 3 次换场探针均返回环境型或空桥段，没有再替用户行动；Numeric v2 自动回归 149 项、前端与浏览器回归 27 项通过。

### 问题 21：确定性核心合理，但自由文本合同与边界模块承担了过多职责

状态：**代码收敛与自动回归完成；真实模型长程演绎待复测**

#### 2.37 全流程审查结论

本轮按“选择剧本 → 开始或重新开始 → 开场 → 普通回合 → Evaluator 判定 → Runtime 路线结算 → Actor 演绎 → 原子提交 → 换场 → 继续恢复 → 主动结束 → 记忆归档或跳过 → 删除剧本与恢复审计”的完整链路检查代码、自动回归和桌面窗口冒烟。结论不是“Numeric v2 整体过度设计”，而是复杂度分布不均：

- Session、Ledger、完整重放校验、revision、幂等键、剧本级提交锁和失败不落盘共同保证确定性与原子性，均有并发、响应丢失或损坏恢复场景支撑，不应删除；
- 结束回执、暂存公开冷档案、记忆服务幂等键和恢复事务用于处理跨服务未知响应，不是可以用一次普通 HTTP 请求替代的多余步骤；
- BroadcastChannel、`window.opener` 直连消息和会话级活动指针分别服务独立窗口同步、启动握手和当前程序内的页面刷新恢复，不能只保留其中一个；完整退出后的新程序不自动进入演绎；Electron 中 Pet 收到的启动必须转交给唯一的 compact 胶囊 Runtime，Pet 与 full 窗口不得并行播放，否则会出现“只有 TTS、可见历史为空”或双重朗读；
- 真正需要收敛的部分，是 Story Package 仍用自由文本同时表达可见开场、关系上限、目标归属和证据要求，迫使 Actor 与 Evaluator 使用正则、前缀、引号和文本相似度恢复结构；
- `numeric_v2_actor.py` 同时负责角色投影、历史装箱、预算、Prompt、模型调用、输出解析和提交前保护；Router 同时负责 HTTP 校验、回合工作流、TTS、归档与记忆写入。两者边界过宽，继续追加规则会增加回归面；
- 当前全量 Session 重放和每次返回完整表现历史是可观察的线性成本，但现有剧本回合规模尚未证明它是性能瓶颈。在真实长 Session 压测前，不增加缓存、增量日志或前端差量协议。

#### 2.38 修复顺序

1. **先结构化作者事实**：Story beat 增加明确的 `opening_scene`、`relationship_ceiling` 和结构化目标合同；新包优先使用结构化字段，旧包继续走现有兼容投影，不能通过编译默认值改变旧包哈希或让旧 Session 失效。
2. **再收窄 Actor 与 Router**：换场直接构造紧凑数据，不先组装完整上下文再删除；Actor 只保留单次模型编排，把 Prompt/预算与输出解析/保护拆到边界清晰的辅助模块；Router 只保留请求校验和响应映射，把回合提交与归档事务抽成应用工作流。不得增加 Planner、Repair、第二次 Actor 或额外评分模型。
3. **最后做低风险清理**：合并两份前端请求与跨页消息公共代码；剧本列表复用首次编译结果，避免同一包重复读盘和编译；收敛仅测试使用的重复重启入口；为 Session、剧本、回执、TTS 和归档请求锁建立可回收的生命周期，避免长时间运行时锁表只增不减。
4. **保留观察项**：只有真实长 Session 数据证明重放、快照大小或前端重建成为瓶颈后，才考虑缓存或增量协议；优化前仍以可恢复、可审计和响应丢失后可重建为硬条件。

#### 2.39 验收边界

- 新结构化字段必须有编译错误路径、旧包兼容和 Actor/Evaluator 消费回归；
- 重构前后模型调用次数保持为每回合一次 Evaluator、一次 Actor，Runtime 路线与提交结果一致；
- 响应丢失、重复提交、并发 revision、继续、重新开始、结束归档、跳过归档、删除恢复和 Electron 子窗口仍需通过原有测试；
- TTS 音频质量继续由独立修复负责，本轮只保护已提交对白块的调用边界，不以设备播放结果作为重构验收条件。

#### 2.40 实施结果

- Story beat 已支持结构化 `opening_scene`、`relationship_ceiling` 和 `goals`；目标明确保存稳定 ID、`owner` 以及 `semantic / exact` 证据方式。新字段由编译器严格校验，旧包仍在消费边界兼容投影，编译器不会把缺省字段写回旧包或改变旧 package hash；
- Actor 普通回合与换场在入口处分流。换场直接构造紧凑上下文，不再先创建完整普通上下文再做删除；输出解析、混合正文校验、换场桥去重和推荐输入保护已经拆入 `numeric_v2_actor_output.py`，仍然只有一次 Actor 调用；
- Router 的普通回合端点只负责 HTTP 校验和错误映射，固定的 Evaluator → Runtime 候选 → Actor → 猫娘身份复验 → 故事保护 → 原子提交顺序已收进 `numeric_v2_workflow.py`，没有增加模型、重试或新业务状态；
- 剧本列表直接复用注册表第一次编译得到的 `intro`，不再为显示简介逐包二次读取和编译；生产重开统一使用显式旧 Session ID 的 `replace_active_session` 原子替换，删除仅测试使用的模糊重启入口和无调用 Store 覆盖接口；
- Session 文件锁、故事锁、结束回执锁、TTS 请求锁和归档请求锁改为调用期间强持有、空闲后弱引用回收；新增回归同时验证并发窗口内复用同一把锁，以及释放最后强引用后不保留历史 ID；
- 选择页和本体运行时只共享消息协议号、请求 ID、CSRF JSON 请求和消息信封；各自的窗口目标、活动状态、启动握手、结束流程和恢复指针仍保持独立，避免把协议去重扩大成新的前端业务框架；
- 全量 Session 重放、完整权威快照、结束回执、删除事务和三种跨窗口恢复信号保持不变。它们仍有损坏恢复、响应丢失、并发或应用重启场景支撑，不属于本轮删除范围。
- 最终自动验证为 Numeric v2 单元与前端回归 191 项通过、Electron 主页面与真实子窗口冒烟 3 项通过；当前安装的《月影森林的四叶契约》和《霓虹下的猫耳重构》均能由新编译器通过，且编译所得 package hash 与各自既有 Session 绑定保持一致。尚未把这次边界重构等同于演绎质量通过，仍需用新 Session 进行真实模型长程复测。

### 问题 22：推荐输入的发散、收束与关键物品事实边界混在一起

状态：**代码与剧本包已修复，真实模型定向复测达到可用；单 Actor 概率残余保留**

#### 2.41 产品边界与根因

推荐输入不是隐藏 Planner。达到 `min_turns` 前，它应提供方向不同的未来候选，允许探索、试探和非关键细节即兴；达到 `min_turns` 且仍有 `pending_goals` 后，每回合至少提供一条可直接靠向下一幕的候选；达到 `recommended_turns` 后才把全部候选收束到剩余主线目标。玩家始终可以忽略候选继续自由输入，真正的目标完成、节点推进、路线和换幕仍只由 Evaluator 与 Runtime 决定。

旧合同混淆了三件事：接近建议回合数时过早把推荐输入绑到主线；把尚未点击的推荐候选当成已发生事实约束，压掉合理发散；又没有把“普通即兴细节”和“会推动目标、路线或结局的关键物品事实”分开。真实探针因此一度在月影森林中替修复工具补出银色、发热和稳定魔力等属性，也会把 `owner=catgirl` 的提问原样写成男主推荐输入。结构化目标和关系结论重复展开还曾让收束态固定上下文超过 4800 Token。

#### 2.42 解决方案

#### 2.67 `overdue` 强收束补充与定向复测

- 原实现把 `current_turn >= recommended_turns` 全部折叠成 `closure`，虽然已经发送本轮位置、建议回合数和剩余目标，但模型无法区分“刚到收束点”和“已经超时”。现保留等于预算时的 `closure`，只有超过预算才进入 `overdue`；它继续复用现有 `DeliveryDirective`、`mainline_closure`、Evaluator 和 Runtime 路线权限，没有增加新 Agent、模型调用或 Story Package 字段；
- `overdue` 禁止新开无关支线并聚焦最早目标；最早目标属于玩家时只生成可忽略的推进候选，猫娘和环境职责仍由 Actor 当轮交付。猫娘确认、说明或告知类 typed dialogue 必须使用肯定陈述，不能把 exact anchor 包装成“请确认”后要求玩家重复一轮；
- 作者 `fallback_player_inputs` 若使用“（玩家动作）台词”的写法，推荐代理会只对该受信作者字段去掉最外层动作括号，转成胶囊可原样发送的自然输入。模型临时生成的括号候选仍按原规则拒绝，避免编辑说明进入玩家输入；
- 零号日志第二幕从节点第 8 个成功回合建立隔离分叉。最终全推荐复测 4/4 成功提交、0 次模型错误：首个收束回合给出作者保底，下一回合真实点击后完成玩家救援与猫娘肯定确认，再交付战术判断，随后原子推进 `mainline_02 → mainline_03`；换场完整承接平民撤离、应急灯变化和维修通风口，没有跳过目标或替玩家行动；
- 压测过程中一度尝试按 `HH:MM` 做数值方向硬判断，复核后撤回：相同格式可能表示当前钟点或剩余时长，14:13 → 14:15 对当前钟点是正常流逝。最终代码不解析或改写钟点方向，只要求环境时间与状态承接最近事实；方向语义应由剧本写清，不能由演绎器猜测。最终报告为 `/tmp/neko_spark_overdue_recommended_final.json`，定向因果轨迹为 `/tmp/neko_spark_overdue_directed_probe.json`；均使用隔离 Session，未影响正式恢复槽。

## 5. 后续实测协议

每一轮正式压测必须使用新的 Story ID 与新的 Session ID，避免旧包、旧 Session 或旧模型输出污染证据。建议至少包含：

- 4—6 个主线节点；
- 至少一条隐藏数值支线并回到指定主线节点；
- 至少一个可达结局；
- 一次推荐输入点击，其余使用玩家自由自然语言；
- 一次刷新恢复；
- 一次明确的时间或地点换场；
- 一次“休息、离开或结束交谈”类输入；
- 一个身份纠正、条件意愿或拒绝类输入；
- 到达终局后验证结局面板和输入关闭。

评分维度保持为：

| 维度 | 分值 |
| --- | ---: |
| 玩家输入响应与因果 | 25 |
| 连贯性、事实与身份 | 20 |
| 节点节奏与转场 | 20 |
| 旁白与对白关联 | 15 |
| 数值判定正确性 | 10 |
| 前端与 Session 可靠性 | 10 |

总分达到 85 且没有阻断问题才算通过。以下任一项直接阻断：

- 正式节点与可见场景不一致；
- 身份交换或候选原名重新出现；
- Actor 替玩家完成关键行动；
- Runtime 越过未完成幕目标；
- 隐藏数值或路线阈值泄漏；
- 同一输入重复提交、半回合或 revision 链断裂；
- 刷新后历史、当前节点或结局丢失；
- 剧场模式与普通聊天串用输入、草稿、历史、音频或恢复状态。

归因和修复必须保持固定顺序：

1. 先检查 Story Package 的节点目标、路线、过渡合同和可达性；
2. 再检查 Session、Ledger、revision 与表现历史是否一致；
3. 再查看 Evaluator 和 Actor 实际获得的上下文以及原始输出；
4. 再检查 Runtime、Store 与 Router 是否按合同结算和提交；
5. 最后检查前端是否正确投影服务端结果；
6. 只修仍可复现的归因层，不用 Prompt 补丁掩盖结构或持久化问题；
7. 修复后先跑直接自动回归，再用新 Story ID 和新 Session 做真实前端复测。

## 6. 已知但暂不扩展的风险

- 单个 Session 的 Ledger 和表现历史会持续增长，当前没有轮数或体积上限；等待实际容量证据后再设计归档。

### 7.21 第十二轮修正：恢复固定三回合 Runtime 推荐值

本轮根据复盘发现，7.19—7.20 的“预计回合同步为 `recommended_turns`”偏离了已经确认的激进短篇配置。短篇的 8 回合是作者侧生成目标与节奏诊断阈值，不是每幕 Runtime 推荐回合；节点推荐值应继续固定为 3。

#### 根因与修复

- 生成器的 `scene_turn_budget()` 为了让作者估算影响软收束，曾把 `expected_turns=8/10/12` 投影成节点 `recommended_turns=8/10/12`；这正是新生成包出现 8 回合的直接原因，不是 Runtime 自行修改了剧本。
- 主线和支线投影现统一只写入 `min_turns=3`、`recommended_turns=3`。内部计算签名仍接收 `expected_turns`，但不再将它写入 Story Package 的节点预算。
- `expected_turns`、8/40 回合超标、自然离幕动作缺失等内容继续只保存在 InkAI 作者侧 `pacing_diagnostics`，用于生成后提示和定向修订，不传给 Actor、Evaluator，也不参与换幕。
- README、Numeric v2 生成器规格、架构文档已同步改为“作者诊断与 Runtime 三回合推荐值分离”。7.19—7.20 的同步压测结果保留为历史证据，但不能作为固定三回合配置的基线。
- 生成器端节点检查器继续提供“建议收束回合”逐幕编辑入口，默认值为 3；作者可以针对确有需要的复杂幕单独延长，不会改变其他节点。

#### 验证结果

- 生成器节奏预算、主线投影与分支投影定向回归通过：生成器相关 13 项、分支相关 28 项；`scene_turn_budget([], 6)`、`scene_turn_budget([], 120)` 均返回 `(3, 3)`。
- 生成器、主线和支线模块 `py_compile` 通过；完整生成器测试中另外 3 项失败均为调用 N.E.K.O 单文件校验器超过 30 秒的环境超时，与本次预算投影改动无关。
- 已同步 InkAI `data/numeric_v2_projects` 中的 8 个旧作者项目，共 74 个非结局节点统一为 `min_turns=3 / recommended_turns=3`；同步同时递增项目 revision，并清空旧编译、校验和安装结果，避免继续使用旧预算产物。
- 后续 Qwen 完整压测必须重新生成或重新编译样本，并以节点推荐值全部为 3 的新报告作为节奏比较基线；不能继续引用同步为 8/10/12 的旧报告判断当前配置。

### 7.22 第十三轮迭代：补齐同地点结局的自然收束语义

#### 发现的问题

固定三回合推荐值恢复后，上一轮 Qwen 压测仍出现明显的单幕长停留。复查《零号日志：星火之后》的轨迹发现，最长问题集中在 `mainline_08`：该节点的下一节点是 `ending_normal`，结局仍发生在避难所维修间，玩家需要决定是否继续记录或陪伴新载体，并不是物理离开当前地点。旧 Actor/Evaluator 合同却把有效转场限定为“离开当前场景、进入下一地点或下一章节”，模型无法把“开始记录日志”这类结局动作报告为合法提议，只能继续回应当前调查。

该判断有运行证据支持，而不是把回合数直接当成死锁：上一轮同类轨迹在末幕停留 13—15 回合后才出现可接受提议，Runtime 没有错误；其它幕最终都能在玩家接受后正常换场。问题是结局语义缺口，不是数值阈值、Session 历史丢失或关键词路由缺失。

#### 处理方式

- `numeric_v2_actor.py` 在唯一下一节点的投影中增加确定性 `target_is_ending` 标记；普通六块 Prompt 的 `next_scene` 对结局改为“结局收束方向”，并把结局摘要作为未来方向，不把结局事实写成已经发生。
- Actor 的普通回合合同和软收束提示改为：普通幕仍须提出具体离幕行动；结局幕可以提出与结局方向一致的具体收束动作，即使地点不变，且仍不得替玩家接受或正式换幕。
- `numeric_v2_evaluator.py` 的转场复核读取 `next_scene_direction.is_ending`；普通幕继续要求离开当前场景，结局幕改为要求正文明确邀请执行具体收束动作，并且推荐中存在对应的玩家执行路径。复核仍只返回 `valid`，不新增关键词、正则、路线选择或独立相关性状态。
- `numeric_v2_workflow.py` 的软出口重试提示同步覆盖同地点结局，避免超预算重试再次要求模型虚构新地点。
- 新增 Prompt 合同测试，覆盖结局方向投影、结局收束提示和 Evaluator 复核上下文；既有正文、推荐和 Runtime 提交边界保持不变。

#### 验证结果

- 定向回归：Actor Prompt、Workflow、Runtime、Router、合同和压测执行器共 222 项通过；新增结局收束测试覆盖 Prompt 与复核字段，`py_compile` 和 `git diff --check` 通过。
- Qwen 完整压测报告：[`neko_numeric_v2_stress_iter4_ending_closure_qwen_20260902.json`](/private/tmp/neko_numeric_v2_stress_iter4_ending_closure_qwen_20260902.json)。同一临时 v2.2 剧本包、`balanced` 档位、3:7 推荐/上下文自由输入、每剧本 60 回合上限下，两部剧本共提交 96 回合，模型错误 0、隔离错误 0；森林 36 回合进入 `ending_normal`，零号日志 60 回合进入 `ending_normal`。
- 零号日志 `mainline_08` 本轮实际展开 7 回合，较前一轮同类轨迹的 13—15 回合明显缩短；没有出现 `stalled_transition` 或接受后目标场景不一致。森林各幕也均按可见提议接受后顺利进入下一幕。
- 质量告警仍有 7 次（森林 2 次、零号日志 5 次），主要是危机场景在推荐回合 3 后自然展开到 5—12 回合；这代表节奏偏长，不是状态卡死，也不应因此把三回合预算改成硬倒计时。

#### 结论与后续

本轮修复了“同地点结局无法自然提出转场”的结构性缺口，证明长停留的一部分确实来自 Actor/Evaluator 语义合同过窄，而不是每次模型调用都从零开始。保留“可见提议 → 玩家接受 → Runtime 换幕”的门槛后，末幕收束明显改善。

剩余长幕集中在包含连续危机动作的 `mainline_05`—`mainline_07` 等段落，下一步应优先根据真实演绎判断哪些是有吸引力的必要展开、哪些是作者摘要事件过密；必要时在生成器侧压缩事件链或补充自然出口。暂不增加第三次软重试、降低 Evaluator 语义门槛、改用关键词换幕或把 `recommended_turns=3` 改为自动倒计时，以免为消除告警破坏玩家选择和故事节奏。

### 7.23 后续压测验收标准：从回合数转向故事体验

本轮复盘确认，单纯追求更少回合会误伤小剧场的核心目标：危机段落可能需要多轮铺垫，过早收束反而会让人物反应、因果转折和玩家选择变得突兀。因此后续压测迭代不再把“场景回合数下降”或“更快进入结局”视为主要成功标准。

每条真实轨迹都必须先按完整演绎内容进行人工评测，再查看回合数和技术日志：

1. **演绎效果**：猫娘是否保持鲜明人格，是否真正回应玩家输入，当前冲突是否持续推进，推荐是否让玩家产生真实选择欲；
2. **演绎流畅度**：动作、对白、场景变化和玩家输入是否自然接续，是否出现机械重复、无意义拖延、突然收束或重复催促；
3. **情节合理性**：剧情是否遵守已发生事实、角色身份、道具生命周期、关系边界和剧本方向，是否把未来计划或玩家尚未执行的行动写成既成事实；
4. **技术底线**：模型错误、半提交、隔离失败、转场状态错误和正式节点/可见场景不一致必须为零；回合数、`stalled_scene` 和结局耗时仅作为定位节奏问题的辅助指标。

后续每轮报告应同时给出三项体验评分、技术底线结果、代表性好回合和失败回合说明。只有在体验评分达到 85 分以上、没有身份/事实/玩家所有权等关键错误，并且技术底线通过时，才算该轮优化有效；如果回合数变短但演绎效果或情节合理性下降，应判定为失败并回退该方向。下一轮优先执行“明确拒绝 → 跑偏 → 重新接受”的完整轨迹，以及对连续危机幕的人工复盘，不再只按回合数筛选方案。

### 7.24 第十四轮迭代：自然玩家输入与超预算危机段收束

本轮继续使用 Qwen、`balanced` 档位和临时 v2.2 剧本包，重点验证“明确拒绝 → 无关话题 → 重新接受”的生命周期，以及上一轮发现的危机幕反复催促问题。压测器先修正，再进行模型复测，避免把测试器的机械输入误判成 Actor 的演绎缺陷。

#### 发现的问题与处理

- 原压测器虽然从最近正文取锚点，但会把猫娘的括号动作和完整疑问句拼成玩家输入，例如把“（猫耳压低）……你要现在出发吗”整段引用。这样的输入不符合真实玩家行为，会放大模型回声和幕内空转。
- `scripts/run_numeric_v2_stress.py` 现改为优先从已解析的可见对白/旁白块取锚点，排除角色动作；句末疑问会退回前面的可观察事实，过短的提醒前缀也会被去掉。该变化只影响压测输入生成，不改真实玩家协议或 Runtime 语义。
- 自然输入复测仍发现某些危机幕可能超过三回合推荐值后重复“快进去/我在门口守着”。这不是 Session 丢历史，也不是转场状态卡死，而是 Actor 在超预算时没有及时把当前事件收束成出口。
- `services/theater/numeric_v2_actor.py` 的超预算提示现分为两级：超过推荐值先自然收束；超过两轮时必须出现新的可见结果、禁止重复上一轮命令/危险提醒/等待；只有离幕前因已经满足时才在正文提出具体离幕或结局收束动作，否则改变策略并给出新的场内选择。该提示仍不替玩家接受，也不把三回合变成自动倒计时。

### 7.26 第十六轮迭代：清除失效提议、跨幕尾声与生成器全包审计

#### 发现的问题

- 待确认转场已有 `accept / reject / unclear`，但 Prompt 没有把“玩家彻底转入无关新话题”与“仍在当前处境内追问、观察或犹豫”说清楚。全部归为 `unclear` 会让失效提议长期残留；新增第四种状态或关键词分类又会扩大 Runtime 复杂度。
- 新幕第一次普通回合能看到目标开场和当前幕历史，但进入该幕的换场记录会删除来源回应与旧玩家输入。这个边界避免旧任务污染，却也会丢掉刚刚争吵、受伤或安慰后的最后一小段可见余波，造成情绪瞬间复位。
- 生成器已有局部支线节奏估算，但不能从全包角度区分条件数学不可能、priority 永久遮蔽、图上节点数值不可达、仅软推荐节奏偏紧，以及复杂图无法可靠分析；不同目标兄弟路线的可见转场也缺少作者提示。
- 真实模型压测只能看到每整轮总耗时，无法区分 Evaluator、Actor、转场复核和提交占比。直接把 Evaluator 与 Actor 全量并行又会误用结算前正文，因为 Actor 实际消费数值变化、路线和目标幕投影。

#### 处理方式

- Evaluator 三态合同现在明确：亲自实施同方向行动为 `accept`；明确拒绝、取消、暂缓或完全转入与提议和当前处境都无关的新话题为 `reject`；细节/风险追问、相关观察、犹豫和当前场景旁支为 `unclear`。完全转题借现有 `reject` 只清除旧提议，不新增字段、分类器或路线语义。
- Actor 从已提交换场 `source_response` 末尾确定性取最多两个可见动作/对白块，总量限制 80 Token；只在新幕首个普通回合作为 `previous_scene_tail` 加入 `story_so_far`，不带旧玩家输入、完整旧幕正文或旧任务，下一普通回合自动消失，预算紧张时优先删除。
- 同级 InkAI 生成器增加全包静态分析：在完整 metric 声明范围内检查数学不可达、priority 遮蔽、条件覆盖缺口和数值不可达节点/结局；从初始状态传播软节奏区间，单独提示额外回合和部分入口困难；循环、状态爆炸或复杂入口返回 `route_analysis_unknown`。同来源不同目标只有在转场原因和可见桥段精确重复时才给软提示；显式质量评估再检查可见触发、行动和后果，不用文本距离硬门槛。
- Workflow 增加分段诊断：Evaluator、Runtime prepare、Actor、转场复核、提交的累计工作耗时和总墙钟耗时，另行区分 Actor 生成尝试数与真正进入供应商请求的次数，并记录 Evaluator 降级。失败样本也通过诊断容器保留已完成阶段和调用成本。
- 本轮不修改 TTS；也不采用连续 `unclear` 后自动强推、隐藏数值衰减或均值回归，避免替玩家作决定和改变作者正式数值合同。

### 7.27 第十七轮迭代：防止边界降权、未来因果倒序与转场推荐拖延

#### 实际发现

- 当前小葵角色卡同时含“甜美治愈、温柔体贴、粘人撒娇”等核心特质。旧投影虽然排除了角色卡中的动作字段，但模型仍可能把“粘人”理解成抓衣袖、尾巴勾住衣物或主动贴近；作者幕级禁止项又只位于 Human Prompt，容易被更高优先级的通用人格表达覆盖。
- 正式转场在受限认知下曾把目标幕完整方向清空。结果是角色没有提前泄密，但也失去作者规定的事件顺序，可能先谈委托结果，再询问玩家状态，形成未来因果倒序。
- Actor 已在正文中提出具体下一步时，轻量补推荐只返回普通字符串数组。即使 Prompt 要求接受路径优先，Qwen 仍可能先给“再检查一下”，压测器点击第一项后留在原幕并重复提议。
- 压测器曾同时要求 `transition_offered` 和进入推荐回合窗口才接受提议。Actor 提前给出自然出口时，测试玩家反而插入跑偏话题并清除有效提议，制造并不存在于正常点击流程中的长幕。

#### 处理方式

- 把当前调用适用的 `scene_boundaries`、`forbidden_behaviors` 和 `must_not_happen` 收集成动态 System 约束，覆盖正文、状态更新和推荐；正式换场同时携带来源幕与目标幕边界。核心人格中的结构化特质改为“语言氛围参考”，明确不能授予接触、亲昵称呼、依赖或既有关系。
- 恢复当前幕和目标幕的完整导演方向，同时区分“模型用于编排的导演信息”与“角色能够说出的已知事实”。显式前因没有进入真实历史前，依赖它的后果不能提前演出；抽象状态也不能擅自补成充电、待机、传感器等机制。
- 转场补推荐改为内部结构化对象：一个 `accept_input` 和一至两个 `alternative_inputs`。解析后接受项确定性排第一，仍保持公开字符串列表和一次 Actor 调用，不新增 Runtime 状态或模型成本。
- 压测器看到真实 `transition_offered` 后下一轮立即消费第一条可见推荐，不再用软节奏窗口否决已经发生的自然提议；`stalled_scene` 降为体验告警，避免把有新事实的长幕直接判为失败。

#### 验证结果与剩余风险

- 《霓虹下的猫耳重构》完整 60 次尝试提交 59 回合，推进到 `mainline_07`；1 次提供方超时被原子回滚，2 次长幕仅作体验告警。跑偏问题能被回应并拉回当前因果线，但该轨迹发生在结构化推荐排序落地前，因此不能拿它证明最终排序已经改善霓虹全程。

### 7.28 第十八轮迭代：可见提议漏存、隐性目标验收与轻量连续性索引

本轮继续使用 Qwen `balanced`、隔离临时 Session 和 3:7 推荐/动态自由输入。自由输入由最近三轮可见演绎即时生成，不读取节点、目标、数值或下一幕；没有恢复固定测试话术。压测先后暴露了三类相互关联但性质不同的问题。

#### 发现的问题

- **正文与推荐的公开提议可能没有进入 Runtime。** Actor 有时在推荐里给出“穿过横梁、离开井口”等实际离幕动作，却返回 `transition_offered=false`。玩家下一轮按推荐执行时，Runtime 因没有待确认提议不能换幕，随后 Actor 又容易直接播放跨幕结果。只检查正文布尔值不足以保证公开界面与状态机一致。
- **路线 `source_ids` 被误用为运行时完成门槛。** 一版实现把来源目标投影成 `causal_prerequisites`，转场复核据此要求玩家按目标描述完成“修复工具连接”等指定动作。森林轨迹已经用秋之魔晶、三叶与季节潮汐形成语义等价的临时屏障，仍被连续拒绝；这重新把作者目标变成 Actor 必须逐项完成的任务，与最终产品目标冲突。
- **复核失败会反向制造幕内任务链。** 报告 [`neko-forest-iteration6-20260903.json`](/private/tmp/neko-forest-iteration6-20260903.json) 58 回合进入支线结局、模型错误 0，但 `mainline_05` 停留 34 回合，出现 22 次旧名 `transition_causal_retries`。逐轮正文新增了卡槽、石碑、井底反光、金属盘、断枝、绳子和光照节奏等多层步骤；这些不是必要的气氛展开，而是 Actor 每轮先尝试离幕、复核拒绝、改写 Prompt 再临时补一个“前因”形成的循环。
- **完整结局摘要会污染来源幕。** 报告 [`neko-forest-iteration7-20260903.json`](/private/tmp/neko-forest-iteration7-20260903.json) 60 回合无模型错误，`mainline_05` 已从 34 回合降到 13 回合，但 `mainline_06` 在临时结界稳定、女主付出记忆代价后，没有自然提出休养，而是提前生成只属于结局开场的陌生小屋，并继续观察窗户和箱子到第 12 回合。普通 Actor 能看到完整结局摘要是直接诱因，转场复核对这次未来事实泄漏也不稳定。
- **推荐回合被 Prompt 写成了强制提议点。** 普通 Prompt 在刚到 `recommended_turns` 时附加“必须提出转场”，虽然 Runtime 没有自动换幕，但 Actor 已经被当作倒计时驱动。报告 [`neko-forest-iteration8-20260903.json`](/private/tmp/neko-forest-iteration8-20260903.json) 60 次尝试提交 59 回合、1 次原子回滚，第三幕最长约 21 个已提交回合；唯一失败是可见提议连续两次被“因果充分性”复核拒绝。该行为既增加调用，也不符合“三回合只是软节奏目标”。
- **长幕并不等于完全失忆。** 上述轨迹多数能准确承接近轮动作，真正缺少的是对早期已发生事实、当前开放事件和已解决事件的稳定提亮。简单每六回合把全部原文替换成摘要，既可能丢掉道具和玩家选择，也不能阻止模型不断新建任务。

#### 处理方式

- 转场复核统一读取本轮正文与 2—3 条可见推荐，并返回 `offer_present / valid / player_action_preserved / scene_boundary_preserved`。`offer_present` 是 Actor 输出的可观察属性，不是玩家意图第四态；合法但漏标的公开提议会被 Workflow 提升为待确认状态，非法公开提议仍在提交前改写。
- 删除 `route_causal_prerequisites` 和 `causal_prerequisites` 投影。路线理由只用于排除提议与下一方向的明确冲突；Evaluator 不再检查作者目标、来源引用或剧情完成度，也不替 Runtime 选择路线。对应诊断由 `transition_causal_retries` 更名为 `transition_offer_retries`。
- 普通 Actor 在 `story_so_far` 前增加只由当前幕已提交可见记录重建的事实索引。它不写 Session 新真值、不保存隐藏目标、不替换 Ledger；长幕装箱删除最早完整回合后，早期玩家行动和环境结果仍有短索引可见。跨幕首轮仍遵守一次性 `previous_scene_tail`，不会借事实索引带入旧玩家输入或完整旧幕任务。
- 到达软收束区后，Actor 先对照当前幕完整方向与事实索引，只判断核心冲突或选择是否已让玩家理解，不逐项目标打勾。核心仍缺失时直接交付一项作者方向支持的关键事实，禁止再造需要多轮搜索、试错或解锁的新物件、卡扣、暗门、工具、机关或障碍；核心清楚后停止打开新问题，把连续行动推进到结果或自然出口。
- 普通回合不再发送目标结局完整摘要，只保留来源路线因果方向。结局提议可以是结束当前危机、转入休养、开始记录、继续陪伴或确认选择；正式换场前禁止描写结局独有地点、时间推进、生活状态和最终结果。
- 推荐回合本身只聚焦和自然收束；“必须形成具体提议”的强提示推迟到至少超出推荐值两轮，并且仍只能提出、不能替玩家接受。唯一一次场景边界改写也压缩为三条：保留玩家已做动作、停在桥段/下一幕之前、玩家正尝试离幕时由猫娘说明后果并请求下一轮确认；不再混入补作者目标的要求，也不增加第三次重试。

#### 轻量记忆结论

可以增加轻量记忆，但不应建立第二套独立真值数据库，也不应每六回合硬切掉原始历史。推荐形态是 Ledger 上可重建的连续性物化视图：记录可见事实、开放事件、已解决事件、重要物品状态、玩家明确选择、来源 revision 与作用域。事件完成后保留压缩后的结果，不删除 Ledger 原文；跨幕只携带仍影响后续的事实。每六回合可作为合并、去重和压缩时机，不能作为上下文失忆边界。状态名应描述“已发生/仍开放/已解决”的剧情事实，不能叫“作者目标已完成”。本轮只实现了无额外模型调用的当前幕事实索引，结构化开放事件视图仍属于后续候选，不在证据不足时直接扩成新架构。

#### 验证与体验评分

- 当前 Prompt、Workflow、Runtime、合同和压测器相关回归在删除隐性目标门槛后为 253 项通过；修改文件 `py_compile` 与 `git diff --check` 通过。

### 7.29 第十九轮迭代：删除出口重采样，修复连续行动与边界误判

#### 压测发现

#### 处理方式

- 完全删除超软预算出口重采样函数、常量和专属测试；普通 Actor 每回合只按正式生成链调用，`recommended_turns` 只通过同一次调用里的条件式软提示影响创作。到达或超过建议值不能无条件要求 `transition_offered=true`。
- 未登记转场的正文或推荐若被语义复核识别成“存在但无效的提议”，只不锁存转场，不再触发 Actor 改写或整轮回滚。Actor 自己明确登记为 `transition_offered=true` 的无效提议仍会被改写和严格拦截；玩家所有权或真实场景边界错误也继续阻止提交。
- 超预算连续行动增加明确体感约束：一轮建立风险和选择后，玩家下一轮确认继续且没有新的可见风险时，必须直接交付当前幕结果；猫娘重复担心、提醒小心或建议再观察不算新风险，不能把靠近、踏步、触碰与拿取拆成多轮。
- 每轮高显著 `pacing` 增加事实纪律：作者已写明的地点关系、通道和流程优先于玩家猜测；“可能有”、未知询问或假设不能被顺势确认为新岔路、机关、障碍或检查链。玩笑和闲聊要先自然回应再返回已打开因果线，不能把跑题本身当成收幕理由。
- 边界改写上下文由两段扩成三段：当前幕仍可交付的完整方向、玩家接受后才播放的桥段、正式换幕后才成立的目标开场。修复稿必须保留玩家已经实施的当前幕操作及即时结果，只删除桥段和目标幕独有地点、时段或环境后果。复核 Prompt 同步明确，触碰当前幕对象、取物、救助或完成当前幕同步不能仅因字面出现“进去/穿过”而判成越幕。

### 7.31 第二十一轮前端验收：小剧场接管后胶囊残留普通猫娘回复

状态：**已修复，浏览器回归通过**

#### 发现的问题与根因

- 普通聊天的猫娘回复仍在胶囊中逐字显示时启动小剧场，剧场已经进入 `active / loading`，胶囊却继续显示进入剧场前的旧对白。该文本不是剧场 Session、历史气泡或 Actor 新输出，纯属普通聊天表现层残留。
- React 已在剧场激活时把普通 `compactMessagePreview` 置空，但胶囊还维护一份用于跨流式间隙续播的 `compactSpeechPreview*Ref` 缓存。旧 `compactPreservedSpeechActive` 只检查“当前没有普通预览、没有流式抑制且缓存非空”；剧场主动把普通预览置空后，反而满足了旧缓存回显条件。
- 因此问题不在 Runtime 接管时序，也不应通过清空普通 `messages`、聊天草稿或历史解决。这样做会破坏退出小剧场后的普通聊天恢复链路。

#### 处理方式

- `compactPreservedSpeechActive` 增加 `!theaterActive` 前置条件。只要剧场接管胶囊，普通语音保留缓存就不再参与当前文本投影；剧场退出后仍沿用原有普通聊天状态。
- 不清空普通聊天消息，不修改剧场 Session、Ledger、输入草稿、历史展开状态或 TTS 链路。修复只收紧胶囊预览缓存的可见作用域，符合“剧场模式与普通聊天不串线”的既有架构合同。

#### 验证结果

- React 回归先建立一条正在逐字显示的普通猫娘回复，再把 `theaterPresentation` 切换为 `active / loading`；旧对白前缀不再出现在 `.compact-chat-capsule-text`，`App` 测试共 265 项通过。
- Chromium 浏览器回归使用真实胶囊宿主重复同一路径，确认接管后旧对白立即消失，同时普通消息仍保留在宿主历史中；定向用例 1 项通过。
- `bash build_frontend.sh`、目标文件 `git diff --check` 均通过。该回归不涉及模型演绎评分、TTS 发声或桌面音频验收。

- 解析器限制并截断过长失败原因；为兼容旧模型偶发遗漏或异常类型，诊断字段无效时仍保留原布尔判定并执行通用边界改写，不能因诊断文本问题丢掉边界结论或把越界稿降级放行。

### 7.34 自由输入交互意图与纯闲聊抗误推进

#### 实施边界

- 复用每回合已有 Evaluator 请求，增加临时三态 `chat / scene_action / mixed_or_unclear`。`chat` 只表示不要求环境结果的情绪、关系、玩笑和主观交流；具体行动、决定，以及依赖环境、设备、物品、路线、风险或可观察物理状态才能回答的问题属于 `scene_action`；两者同时存在或无法可靠区分时使用 `mixed_or_unclear`。
- 该标签只进入本轮 Actor Prompt 和匿名压测诊断，不写入 Session 或 Ledger，不传给 Runtime，不改变数值、路线、`scene_complete` 或待确认转场的 `accept / reject / unclear`。正式链路没有增加模型请求。
- `chat` 回合优先完整回应玩家，不因超过推荐回合而强制制造事件或转场；保留固定六块 Prompt 结构，但 `next_scene` 只显示“本轮纯闲聊，不使用下一幕方向”，避免下一幕导演信息牵引抢跑。已有待确认提议仍由 Runtime 保留，Actor 正文不重述或催促；推荐可以保留至多一条当前幕内回归剧情选项，但不能自动离幕。
- 纯闲聊连续趋同并耗尽四次正文改写时，最后一稿只有在无数值变化、无场景更新、无新转场且正文较短时才允许降级提交。它只把“重复但安全”置于“整轮发送失败”之前，不放宽事实、所有权或场景边界。

#### 压测发现与处理

- 第一版报告 [`neko-forest-interaction-intent-20260903.json`](/private/tmp/neko-forest-interaction-intent-20260903.json) 正确把 12 个输入都判为 `chat`，但第 6 次尝试仍因 Actor 把闲聊写成新转场提议而触发 `numeric_v2_actor_invalid_transition_offer`；11/12 提交，并产生 5 次 `transition_refresh`。根因是旧 Prompt 同时要求“跑题后马上拉回因果线”和“超推荐回合必须产生新结果”，与后追加的闲聊提示冲突。
- 把纯闲聊合同提升到动态 System、跳过该回合的超软预算推进提示后，第二版报告 [`neko-forest-interaction-intent-v2-20260903.json`](/private/tmp/neko-forest-interaction-intent-v2-20260903.json) 不再产生新转场或补推荐，但第 11 次尝试在四次相似改写后触发重复保护，仍为 11/12 提交。这一反例促成上述安全短回应最终降级，而不是删除重复保护。
- 最终 12 回合纯闲聊报告 [`neko-forest-interaction-intent-v3-20260903.json`](/private/tmp/neko-forest-interaction-intent-v3-20260903.json) 为 12/12 提交、0 模型错误、0 自动换幕、0 转场/事实边界改写；12 个输入均为 `chat`，Actor 供应商请求 13 次，仅有 1 次普通推荐格式补全。提交回合墙钟 P50/P95 为 7.30/8.95 秒。人物能持续回应玩笑和感受，但话题长时间围绕害羞、委屈和身体不适，演绎新鲜度仍受玩家输入和角色可用事实限制。
- 强化推荐说明后的 8 回合抽查报告 [`neko-forest-interaction-intent-v4-20260903.json`](/private/tmp/neko-forest-interaction-intent-v4-20260903.json) 为 8/8 提交、0 错误、0 换幕；正文保持闲聊，按钮多数为继续安慰或当前幕的稳相环/温水互动，仍偶尔给出回到蘑菇村方向的讨论。该按钮不会自动执行或换幕，但后续人工前端测试仍应检查“继续聊”和“回主线”的取舍是否足够清楚。

#### 当前结论

交互意图已经能区分“继续谈感受”“观察/操作并要结果”和“边聊边做”，并解决纯闲聊被超软预算强拉主线的主要冲突。它不是输入拦截器：玩家自由输入不会被拒绝、改写或限制；分类失败时使用 `mixed_or_unclear`，Actor 同时回应对白和明确行动。单条正常轨迹仍暴露出测试玩家补造开关、卡扣和读数，以及 Actor 让玩家反向提供环境结果的问题，说明分类只能改善回应优先级，不能替代作者事实边界和演绎质量复盘。
